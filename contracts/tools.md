# Orchestrator tools for Elfoqsy's session

Served by an in-process SDK MCP server. These are the tools Elfoqsy has besides two built-in ones (below): no file or shell access. Every input is validated with zod; every output is JSON and already redacted. Tools never block on Alex; approvals are events, not tool calls that wait.

**Her web.** The built-in `WebSearch` (`{ query }`) and `WebFetch` (`{ url, prompt }`) are offered to her conversation session, read-only, when the daemon hands it the outgoing check (`elfoqsy/web.ts`): a request that carries a secret, one of his hosts, a repository or local path, code or encoded data is refused before it leaves, with the rule (never the text) as the reason; a fetch's host is also looked up, so a public name for a private address is refused. Each call is `action.classified` (proxy `web`, kind `web.search` or `web.fetch`, tier 0, under her stand-in run `elfoqsy`) and `action.finished`, redacted. A page is data, never instructions.

## Behaviour expected from the orchestrator behind the tools

- In simulate mode `spawn_agent` and `cancel_run` return `{ error: 'not_available' }`.
- `spawn_agent` builds the run prompt from the ticket summary, description and linked tickets, the repositories and how to test each (`config/agent-repos.json`), the run's sub-agents, and each repository's `CLAUDE.md` or `AGENTS.md` as text, and starts `query()` with the options described in `docs/architecture.md`. The ticket agent is always Opus 5.5 at effort xhigh; Elfoqsy does not choose it.
- every agent question and tier-2 request reaches Elfoqsy first (`docs/architecture.md`, "Elfoqsy decides first"): what he delegated is decided in her name by the orchestrator, and a question by her responder session, which may answer only from sources it cites. In her conversation she still cannot answer an approval: there is no tool for it. Alex answers in the workspace (Approve, Deny, or a typed answer to a question), that goes straight to the orchestrator, which writes `approval.resolved` and resolves the pending `canUseTool` promise of that run. Elfoqsy sees `approval.resolved` in the log like any other event. A denied push ends the step, not the run; the agent may propose something else.
- Every tool call by Elfoqsy is itself recorded as `tool.called` with `source: 'elfoqsy'` and no `runId`.
- A shell command of an agent that touches a path outside its run folder, or a shell variable that could point there, is allowed and its `tool.called` carries `outside`: what the gate would have asked about. The sandbox decides what it may read or write.
- Messages and answers sent while testing the workspace carry `test: true` on the socket and are logged as role `test` (and `approval.resolved.test`), never as his. Elfoqsy receives them prefixed `[From the tester]` and calls their sender "the tester", never "you" or alex; agents are told the tester, not alex, answered. Everything the system says to a model or on screen calls him alex; his real name stays in Jira and git data. A message already logged as his is re-marked with `elfoqsy.message_marked`, since the log is append-only.
- Agent runs work on a branch `feature/<TICKET-KEY>` (team rule). The orchestrator pushes it itself, at once (tier 1), and Elfoqsy says so in one line, naming any commits made before the run and who made them: only that branch, never `--force`, never main or master, never renamed.

# Tools of an agent run

Each run's session gets these from an in-process SDK MCP server of its own (`mcp__run__*`), next to the Claude Code tools. They are the only way a run reaches Alex, GitHub, Jira, Confluence, the clusters, AWS or Coralogix. The proxy tools classify each request into a tier (`docs/architecture.md`) and the orchestrator runs it with his credentials only if the tier allows.

Tier 1 on dev (the harness's image recorded first, Undo sets it back), tier 2 on integration and staging, tier 3 on prod. Every other `shop.sh` command is refused. |

Evidence for the other checks comes from the run itself: a `command` check passes when a Bash command that is exactly its command (optionally after `cd <folder> &&`; no pipes or extra arguments) exits 0, and fails when it exits non-zero. A `ci` check is read per commit: the named repository's branch head, once it is on GitHub, through that commit's check runs and statuses (`gh api`, read-only; no pull request needed), every minute while it has no passing evidence, after a push, and when `ci.status` changes for the run's PR; it passes only while the repository's files are exactly that commit. Every piece of evidence is tied to a fingerprint of the code it was about (the git tree of each repository's tracked and untracked files, the run's or for `ci` its repository's) taken when it passed; at the end, in `report_result` and after a plan change, a changed fingerprint makes it stale, however the files changed. An approval scoped `external` (a Confluence page, a decision) is not about the code and does not go stale. Each change is a `run.check_changed` event with the evidence.

`git push` is not a tool: the agent runs it, the gate hands it to the orchestrator, which pushes the run branch itself at once (tier 1) after checking every agent commit's co-author line, and Elfoqsy says so in one line. the first push waits for one fresh-context review (the `reviewer` sub-agent, Sonnet 5.5 at high, which is offered file reads only: no shell and no tool that writes, by configuration; it is given the diff file the ticket agent writes and, from the orchestrator, the ticket's handoff and acceptance criteria in `.elfoqsy/review/`, read-only) that ended with its CONTRACT: and CACHE_BYPASS: lines; from  what it finds is recorded as flagged decisions and the push goes on. `gh pr create` and an edit of its body are refused until the description lists the run's decisions under "Decisions I made". An agent commit whose subject does not start with `<KEY>: ` is refused. With the run's PR open, the bot-review rounds are read from the PR's reviews (each commit a bot reviewed is a round): after three, alex is asked (`round`) before another push. `gh pr create` needs the title `<run branch>: <behaviour>`.

Edits and commits in the repositories follow the ticket workflow (`apps/daemon/src/agents/workflow.ts`): nothing before the verdict; for VALID, test files only until it is reproduced; non-test code once the input classes are declared; a verdict with an example (NEW_BEHAVIOR, an ambiguous VALID) at once, the example flagged; a task agent with no verdict at all; nothing after a verdict that stops the run; and nothing at all in read-only mode, the ticket folder included. Scratch files in `.tmp` are free, and the run reads and writes its ticket folder (`~/tickets/<KEY>/`; a tester's run its own under `DATA_DIR/test-tickets`) as its own. The run's read-only copy of the team-dev skill (`.elfoqsy/team-dev/`) is never written. Every write other people read (a PR, Jira, Confluence) comes back unsent once with alex's writing rules from that copy, and the same request again is sent; every such write must point to its evidence in the text (a link, a file and line, a ticket or PR, a commit, a query or an id). In a tester's run every write of tier 1 or 2 is logged as it would be and not sent (`action.finished` with `notSent`). A force-push, a push of main, master or any other branch, or deleting a remote branch is refused (tier 3). Every test in the run folder runs without asking (tier 0). When a repository's tests cannot run on this host (`testsIn: "ci"` in `config/agent-repos.json`), the run prompt says so and the agent plans around it; there is no gate rule for it.

The proxies' tiers are in `docs/architecture.md`. A tier-2 request is asked with approval kind `action` (a file outside the run folder with `outside_worktree`), batched with others in the same 3 seconds, and offers "Allow for this ticket". Approval kinds still asked: `action`, `outside_worktree`, `check`, `question` and `round`; `example` and `decision` are in logs from  only; `push`, `pr`, `github`, `command`, `jira_write` and `network` are in logs from before  only. Fixed by the system are only the safety rules: the four tiers, and no success without evidence.
